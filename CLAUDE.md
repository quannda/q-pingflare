# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm install                    # root install; frontend is an npm workspace
npm run dev                    # backend (8787) + frontend (5173) + cron simulator, concurrently
npm run dev:backend            # wrangler dev --test-scheduled
npm run dev:node               # tsx watch src/server.ts — the Node/SQLite runtime instead of Workers
npm run db:migrate:local       # apply drizzle/*.sql to the local D1
npm run db:generate            # drizzle-kit generate after editing src/db/schema.ts

npx tsc --noEmit               # backend typecheck (what CI runs)
npm run check -w frontend      # svelte-check (what CI runs)
npm run build                  # frontend build → frontend/build (consumed by the Worker's ASSETS binding)
npm run build:server           # tsup → dist-server/server.js (the Docker/Node artifact)
```

There is no test suite. CI (`.github/workflows/ci.yml`) is typecheck + build + `npm audit --audit-level=high` only — run both typechecks before claiming a change is done.

Deploying to Cloudflare has its own skill: `.claude/skills/deploy/SKILL.md`. Read it before any `wrangler deploy` — the Worker name and migration ordering are both load-bearing.

Cron locally: `curl "http://localhost:8787/__scheduled?cron=*+*+*+*+*"`. Authenticated manual trigger in any runtime: `POST /api/cron/run`.

## Architecture

One Hono app, **two runtimes**, sharing everything under `src/routes`, `src/services`, `src/notifications`, `src/db`:

| | Cloudflare Workers | Node / Docker |
|---|---|---|
| Entry | `src/index.ts` | `src/server.ts` |
| DB | D1 (`env.DB`) | better-sqlite3 behind `src/db/shim.ts`, cast to `D1Database` |
| Cron | `scheduled()` + `[triggers]` in `wrangler.toml` | `node-cron` in-process, every minute |
| Static | `ASSETS` binding, `run_worker_first = true` | `serveStatic` from `frontend/build` |
| KV cache | optional `CACHE` binding | always absent → cache falls through |

**Both entrypoints register the route table independently.** Adding a router means editing `src/index.ts` *and* `src/server.ts`; forgetting the second one silently breaks only the Docker build.

The SQLite shim implements just the D1 surface drizzle uses (`prepare/bind/first/run/all/raw/batch`). Prepared statements are memoised on purpose — see the comment in `shim.ts`; re-preparing broke `raw()` and made every drizzle read come back empty.

Node-only APIs are unavailable in Workers and vice versa: `cloudflare:sockets` (used by `src/notifications/email.ts` for SMTP) is aliased to `src/shims/cloudflare-sockets.ts` by `tsup.config.ts` for the Node build.

### Request flow

`src/cron.ts` `runCron()` is the heart: load settings → amortised retention → select active monitors whose `interval` has elapsed → per monitor, `checkHttp` / `checkHeartbeat` → insert a `status_logs` row → `recordCheck` (upsert the `daily_stats` bucket) → `processAlert` → collect status transitions and invalidate their cache keys.

`src/services/alert-manager.ts` owns all alert state machinery: failure tolerance, incident open/close, surge protection, reminder cadence. Notification channels are loaded lazily because most checks dispatch nothing.

## Schema changes require three edits

The schema lives in three places and they must stay in sync:

1. `src/db/schema.ts` — drizzle definitions (the types everything else uses).
2. `drizzle/*.sql` — generated by `npm run db:generate`, applied by the `db:migrate:*` scripts.
3. `src/db/migrate.ts` — `ensureSchema()`, the runtime bootstrap. It runs the `SCHEMA_SQL` DDL batch on first request so a fresh Cloudflare or Docker deploy self-provisions with no migration step.

For `ensureSchema` specifically: new tables/indexes go in `SCHEMA_SQL` (all `IF NOT EXISTS`), new columns on existing tables go in the `alterStatements` list (each wrapped in try/catch for the already-exists case), and **`SCHEMA_VERSION` must be bumped** — otherwise the fast path (`schema_version` row ≥ current) short-circuits and the DDL never runs on existing deployments.

## Free-tier budget is a design constraint

The Cloudflare deployment targets the free tier, and several non-obvious decisions exist only to protect that budget. Don't undo them without doing the arithmetic:

- **Writes set the check interval.** ~6 rows per check; the `[triggers]` cron in `wrangler.toml` is the floor on all monitor intervals. `*/5` (default) ≈ 35k rows/day at 20 monitors; `*/2` is the tightest safe setting against the 100k/day limit.
- **`daily_stats`** is a per-monitor-per-UTC-day rollup so a 90-day chart reads 90 rows, not every log in the window. Windows ≤ 2 days still read raw logs, for second-precision. Backfill/repair: `POST /api/settings/rebuild-stats`.
- **Retention** runs at most once a day (`last_cleanup_at` setting, claimed before the work) and deletes per monitor so the `(monitor_id, checked_at)` index seeks instead of scanning.
- **`src/cache.ts`** — KV caches only historical aggregates, and every operation degrades to a direct compute when `CACHE` is unbound or KV errors. KV *writes* are the scarce resource (1,000/day), so a write only happens on a miss. Current up/down state is deliberately never cached; bump the `v1` segment in `cacheKeys` to invalidate every entry after a payload shape change.
- **Aggregate endpoints are batched**: `/api/monitors/overview` and `/api/monitors/:id/summary` each replace what used to be N per-monitor requests. Prefer extending them over adding new per-monitor fetches. `router.get('/overview')` must stay registered before `'/:id'`.
- **Frontend polling** goes through `frontend/src/lib/poll.ts`, which skips ticks while the tab is hidden. Use it rather than a bare `setInterval`.

## Conventions

- Timestamps are **unix seconds** (`Math.floor(Date.now() / 1000)`) everywhere in the DB and API. `daily_stats.day` is `checked_at / 86400`.
- SQLite/D1 has no booleans — drizzle maps integer columns, and DDL defaults are written `DEFAULT true` / `DEFAULT false`.
- Auth is a bearer JWT (`jose`) verified by `src/middleware/auth.ts`; routers apply it with `router.use('*', requireAuth)`. Public routes (`/api/public/status`, `/h/*`, `/api/auth/*`) do not.
- `AUTH_DISABLED=true` (env var, both runtimes) turns `requireAuth` into a no-op for deployments fronted by Cloudflare Access or an SSO proxy. The frontend learns about it from the public `GET /api/auth/config` and skips the `/login` redirect. Anything that gates on auth must go through `requireAuth` / `isAuthDisabled` rather than checking the header itself.
- Notification credentials are encrypted at rest with `ENCRYPTION_KEY` (AES-GCM, `src/utils.ts`). `SENSITIVE_FIELDS` in `src/utils.ts` declares which config keys per channel type get encrypted — a new channel with a secret must be listed there.
- Adding a notification channel: a `src/notifications/<name>.ts` sender, a case in the `sendNotification` switch, `SENSITIVE_FIELDS`, `notify.*` locale keys, and the frontend `NotificationForm.svelte`.
- Required secrets in every runtime: `ADMIN_USER`, `ADMIN_PASS`, `JWT_SECRET`, `ENCRYPTION_KEY` (the last two ≥ 32 chars) — with `AUTH_DISABLED` only `ENCRYPTION_KEY` is. Local: `.dev.vars`.

## i18n

Translations live in `/locales/*.json` (flat key → string, `{placeholder}` interpolation) and are consumed by **two static import maps** that both need editing when a locale is added:

- `frontend/src/lib/i18n.ts` — UI strings, plus locale detection/persistence.
- `src/notifications/messages.ts` — the `notify.*` keys used in outgoing alerts, resolved server-side from the `locale` setting.

`$locales` is a Vite alias to `../locales`, allowlisted in `frontend/vite.config.ts` (`server.fs.allow`). Full procedure: `docs/LOCALES.md`.
